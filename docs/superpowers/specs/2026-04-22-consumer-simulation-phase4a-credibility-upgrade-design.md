# Consumer Simulation Phase 4A Credibility Upgrade Design

## 1. Goal

Phase 4A upgrades `consumer_test` from a research-grade simulation workflow into a more trustworthy decision system by improving source quality governance, evidence validation, conclusion confidence, and replay-based calibration.

The design target is not "more test types" yet. Phase 4A focuses on one product promise:

> when the system says a claim resonates, a risk is real, or a strategy works better, the user should be able to see how strong that conclusion is, what evidence supports it, and whether similar cases replay consistently.

## 2. Scope And Explicit Exclusions

### 2.1 In Scope

- source quality scoring for Lane A and Lane B research sources
- stronger public-web source governance before findings enter the project workspace
- retrieval evidence validation before findings are surfaced to reports or comparisons
- finding-level and report-level confidence scoring
- benchmark replay for minimal repeatability and calibration checks
- UI exposure of evidence sufficiency, confidence, and replay status

### 2.2 Out Of Scope

- packaging / A-B / pricing test expansion
- DingTalk or external focus-group connectors
- large-scale performance replatforming
- live web search during every propagation round
- full ML-based evaluation pipelines or external annotation platforms

## 3. Why Phase 4A Must Come Before Other Upgrades

Phases 1 through 3 already completed the core workflow:

- consumer brief ingestion
- dual-source research grounding
- branchable interventions
- social sandbox propagation
- research asset export and comparison

The weakest remaining layer is not workflow coverage. It is decision trust.

Today the system can explain *what happened* and *why it likely happened*. Phase 4A must make it better at answering:

- how reliable is this source?
- how strong is this evidence chain?
- how confident is this finding?
- has this conclusion held up when replayed against a benchmark case?

Without that layer, expanding test types would create more surface area but not more decision quality.

## 4. Cross-Cutting Principles

- MiroFish remains the primary product backbone.
- `consumer_test` remains an explicit branch of the existing product.
- user-uploaded materials still outrank public-web supplements by default.
- no finding should appear in a report without an inspectable evidence chain.
- confidence must be computed from structured signals, not only prose generated by the model.
- replay and calibration must be repo-local and reproducible in the first version.
- `project_type=default` must remain unchanged.

### 4.1 Consumer-Only Gating

Phase 4A extends shared routes, but the new behavior must only activate when:

- the project exists
- `project.project_type == "consumer_test"`
- the request is already on a consumer-aware flow such as:
  - consumer graph build
  - consumer simulation prepare
  - consumer summary
  - consumer report / comparison

Default projects must continue to use the existing MiroFish route path without invoking:

- source quality scoring
- evidence validation
- confidence scoring
- benchmark replay

## 5. Product Outcomes

When Phase 4A is complete, the current workflow should improve in five visible ways:

1. sources are labeled by trust, freshness, and coverage
2. weak or mismatched retrieval evidence is flagged before it becomes a highlighted finding
3. reports show confidence and evidence sufficiency instead of only qualitative claims
4. comparison outputs state whether differences are strongly supported or weakly supported
5. benchmark replay can rerun a saved case and compare current outputs against a known baseline

## 6. Module Design

### 6.1 Source Quality Evaluator

Purpose:

- score every research source before or during finding distillation

Responsibilities:

- assign `trust_tier`
- assign `freshness_score`
- assign `source_confidence`
- assign `coverage_tags`
- record why the score was assigned

Recommended files:

- `backend/app/services/consumer/source_quality.py`
- tests in `backend/tests/consumer/test_source_quality.py`

Integration points:

- called from `resolve_research_findings()` and `build_research_snapshot()`
- persisted through `project_research_persistence.py`
- summarized into `project.consumer_context["research_snapshot"]`

Key rules:

- user uploads default to higher trust than anonymous public-web results
- trusted domains or structured documents can receive confidence boosts
- stale or low-detail web results should be penalized
- quality scoring must be deterministic for the same input snapshot

### 6.2 Lane B Governance Upgrade

Purpose:

- filter and normalize public-web supplementation before it becomes a `ResearchFinding`

Responsibilities:

- enforce minimum snippet quality
- reject duplicate or near-duplicate low-value results
- downgrade sources with weak provenance
- persist governance decisions into retrieval traces

Recommended files:

- `backend/app/services/consumer/lane_b_provider.py`
- `backend/app/services/consumer/retrieval.py`
- tests in `backend/tests/consumer/test_lane_b_provider.py`

Integration points:

- governance runs inside Lane B result normalization before findings are distilled
- accepted/rejected metadata is appended to `RetrievalTrace`
- downstream finding distillation only uses accepted traces

Key rules:

- Lane B may fill gaps, but it should not dominate Lane A
- governance decisions must be visible in trace data
- public-web supplement should preserve the raw result and the accepted normalized result

### 6.3 Retrieval Evidence Validator

Purpose:

- verify that a distilled finding is actually supported by cited snippets and retrieval traces

Responsibilities:

- detect unsupported findings
- detect weak snippet-to-finding alignment
- compute evidence sufficiency
- attach validator output to findings and report context

Recommended files:

- `backend/app/services/consumer/evidence_validator.py`
- tests in `backend/tests/consumer/test_evidence_validator.py`

Integration points:

- called after `Finding Distiller` and before report context assembly
- called again during comparison synthesis when two confidence-bearing snapshots are compared

Key rules:

- a finding without aligned snippets should be marked weak, not silently accepted
- validator output should distinguish:
  - `supported`
  - `weak_support`
  - `insufficient_support`
- validator output must remain machine-readable

### 6.4 Confidence Scoring Layer

Purpose:

- turn source quality, evidence validation, propagation consistency, and comparison support into structured confidence fields

Responsibilities:

- compute `finding_confidence`
- compute `report_confidence`
- compute `comparison_confidence`
- provide reason codes for each confidence result

Recommended files:

- `backend/app/services/consumer/confidence_scoring.py`
- `backend/app/services/consumer/scoring.py`
- `backend/app/services/consumer/report_context.py`
- tests in `backend/tests/consumer/test_confidence_scoring.py`

Module boundaries:

- `confidence_scoring.py`
  - pure credibility logic
  - aggregates source quality, evidence validation, and replay alignment inputs
- `scoring.py`
  - attaches credibility output to run-level simulation summaries
- `report_context.py`
  - formats already-computed confidence into report-friendly structures

This split is required to avoid circular dependencies between simulation scoring and report rendering.

Key rules:

- confidence is not probability of truth; it is structured decision confidence
- confidence must be explainable through inputs:
  - source quality
  - evidence sufficiency
  - cross-signal consistency
  - replay alignment when available
- the UI should never show a naked confidence label without a supporting explanation

### 6.5 Benchmark Replay Registry

Purpose:

- let the system rerun saved benchmark cases and compare new outputs against expected qualitative baselines

Responsibilities:

- register benchmark cases from existing research packs or project snapshots
- replay a benchmark with the current stack
- compare current result against saved expectations
- record drift or alignment

Recommended files:

- `backend/app/services/consumer/benchmark_registry.py`
- `backend/app/services/consumer/benchmark_replay.py`
- tests in `backend/tests/consumer/test_benchmark_registry.py`
- tests in `backend/tests/consumer/test_benchmark_replay.py`

Key rules:

- first version stays repo-local
- benchmark expectations should use stable derived signals, not brittle raw text matching
- replay artifacts must preserve:
  - source pack lineage
  - prompt/runtime context summary
  - replay result timestamp

Stable derived signals for the first version:

- `acceptance_band`
  - one of `positive_lean`, `mixed`, `negative_lean`
- `top_resonance_labels`
  - normalized labels derived from top resonance findings
- `top_risk_labels`
  - normalized labels derived from top risk findings
- `misread_present`
  - whether meaningful misread amplification occurred
- `clarification_recovery_present`
  - whether clarification recovery occurred
- `cascade_band`
  - one of `contained`, `spreading`, `takeover`

Replay alignment should compare these stable signals instead of raw generated text.

### 6.6 Report And UI Confidence Adapter

Purpose:

- surface trust and confidence signals to Step 2, Step 4, and Step 5 without replacing the current workflow

Responsibilities:

- show research source quality summary in Step 2
- show finding confidence and evidence sufficiency in Step 4
- show benchmark replay alignment where available
- generate Step 5 prompts that reference weak evidence or low-confidence conclusions

Recommended files:

- `frontend/src/components/Step2EnvSetup.vue`
- `frontend/src/components/Step4Report.vue`
- `frontend/src/components/Step5Interaction.vue`
- `frontend/src/utils/consumerMode.js`
- `frontend/src/api/report.js`
- locale updates in `locales/en.json` and `locales/zh.json`

Key rules:

- the first screen should stay readable
- confidence UI should help prioritization, not overwhelm the user
- low-confidence findings should still be visible, but clearly labeled

## 7. Data Model Additions

The first version should reuse existing model fields where possible instead of introducing duplicate semantics.

- `ResearchSource.trust_tier`
  - keep and reinterpret as the primary trust bucket field
- `ResearchFinding.confidence`
  - keep as the numeric storage field
  - add structured companion fields for label and reasons rather than replacing it

### 7.1 Source Quality Snapshot

Recommended fields:

- `source_id`
- `source_type`
- `trust_tier`
- `freshness_score`
- `source_confidence`
- `coverage_tags`
- `quality_reasons`

Storage note:

- this snapshot augments `ResearchSource.metadata`
- project-level persistence may materialize a `source_quality.json` summary for repo-local lookup, because MiroFish currently uses file persistence for consumer artifacts rather than a database-backed query model

### 7.2 Evidence Validation Result

Recommended fields:

- `finding_id`
- `validation_status`
- `evidence_sufficiency`
- `aligned_snippet_ids`
- `missing_support_reasons`
- `validator_notes`

Relationship:

- one validation result belongs to one `finding_id`
- validation may reference one or more `source_id` values through aligned snippets and traces

### 7.3 Finding Confidence

Recommended fields:

- `finding_id`
- `confidence_label`
- `confidence_score`
- `confidence_reasons`
- `support_summary`

Relationship:

- one confidence result belongs to one `finding_id`
- it is computed from:
  - `ResearchFinding.confidence` as the numeric base field
  - source quality inputs
  - evidence validation output
  - optional replay alignment inputs

### 7.4 Benchmark Replay Result

Recommended fields:

- `replay_id`
- `benchmark_id`
- `project_id`
- `simulation_id`
- `alignment_status`
- `metric_deltas`
- `drift_signals`
- `replay_summary`

Relationship:

- one replay result belongs to one `benchmark_id`
- a replay may reference:
  - one source pack lineage
  - zero or one `project_id`
  - zero or one `simulation_id`

## 8. API Direction

### 8.1 Existing Route Extensions

Extend existing consumer flows so source quality and evidence validation are available in:

- `POST /api/graph/build`
- `POST /api/simulation/<simulation_id>/prepare`
- `GET /api/simulation/<simulation_id>/consumer-summary`
- `POST /api/report/generate`
- `POST /api/report/compare`

Expected consumer-only response additions:

- graph build / prepare payloads:
  - `source_quality_summary`
  - `evidence_validation_summary`
- consumer summary payloads:
  - `finding_confidence_summary`
  - `low_confidence_findings`
  - `evidence_sufficiency_summary`
- report / comparison payloads:
  - `confidence_label`
  - `confidence_score`
  - `confidence_reasons`
  - `support_summary`
  - `replay_alignment`

### 8.2 New Benchmark Routes

Recommended additions:

- `POST /api/report/benchmarks/register`
- `GET /api/report/benchmarks`
- `GET /api/report/benchmarks/<benchmark_id>`
- `POST /api/report/benchmarks/<benchmark_id>/replay`
- `GET /api/report/benchmark-replays/<replay_id>`

These routes should stay consumer-specific in behavior while still living under existing report infrastructure.

## 9. Storage Direction

### 9.1 Project Research Workspace

Continue using:

`backend/uploads/projects/<project_id>/research/`

Additional persisted artifacts:

- `source_quality.json`
- `evidence_validation.json`

These files are acceptable because the current consumer stack already persists project-local research artifacts as JSON under `backend/uploads/projects/<project_id>/research/`. Phase 4A should extend that same repo-local persistence pattern instead of introducing a partial database migration.

### 9.2 Benchmark Workspace

Recommended root:

`backend/uploads/benchmarks/`

Planned artifacts:

- `benchmark_manifest.json`
- `expected_signals.json`
- `replay_runs/<replay_id>.json`

## 10. User Workflow Impact

### 10.1 Before Simulation

The user can still create a `consumer_test` project in the same way, but Step 2 should now tell them:

- how many sources were accepted
- which trust tiers dominate the research snapshot
- whether the snapshot is source-light or evidence-light

### 10.2 After Simulation

Step 4 should now tell them:

- which findings are high-confidence or low-confidence
- which findings are well-supported vs weakly supported
- whether key recommendations rest on fragile evidence
- whether a replayed benchmark aligns or drifts

### 10.3 During Follow-Up

Step 5 should help users ask better questions, such as:

- which recommendation is weakest and why
- which risk signal depends too heavily on public-web evidence
- what changed when replay alignment degraded

## 11. Error Handling

- if old project research artifacts do not contain Phase 4A fields, loaders must backfill them as `unknown` / `not_scored` instead of failing
- if source quality scoring fails, preserve the source and mark quality status as unavailable
- if evidence validation fails, findings should degrade to unknown confidence instead of disappearing
- if benchmark replay fails, the primary simulation result remains valid; only replay status becomes failed
- if no benchmark exists, the UI should show "not replayed" instead of implying a negative result

## 12. Acceptance

Phase 4A is complete when all of the following are true:

- project research artifacts include source quality summaries
- public-web findings are filtered through stronger governance and persist their decisions
- findings expose machine-readable evidence validation results
- report context and comparison context expose confidence fields and reason codes
- Step 2 / Step 4 / Step 5 surface confidence and evidence sufficiency without breaking the current flow
- benchmark cases can be registered and replayed with persisted replay artifacts
- backend tests and targeted frontend tests cover the new credibility fields
- `project_type=default` remains unaffected
- existing consumer projects without Phase 4A artifacts can still be opened and reported on

## 13. Recommended Execution Order

1. `Phase 4A-1`: Source quality model and Lane B governance upgrade
2. `Phase 4A-2`: Evidence validator and confidence scoring
3. `Phase 4A-3`: Report/UI confidence exposure
4. `Phase 4A-4`: Benchmark registry and replay
5. `Phase 4A-5`: Final acceptance, docs, and handoff

## 14. Definition Of Done

Phase 4A is done when the current `consumer_test` workflow can answer not only "what happened" and "why it happened", but also:

- how trustworthy the evidence was
- how strong the conclusion is
- whether the result aligns with replayed benchmark expectations
